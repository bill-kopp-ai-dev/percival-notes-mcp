## Limites e pendências

- **O scan não qualifica distribuição nem runtime.** Vale somente para o image ID acima e para a base de vulnerabilidades datada. Não há digest OCI publicado; publicação segue fora do escopo.
- **O relatório bruto do Trivy e o SBOM não foram exportados para este repositório.** O host guardou os artefatos e expõe apenas os hashes acima. Isso segue o precedente registrado no tracker canônico para a imagem Weather 0.10.0 (`pblabs-mcp-index/docs/f3-tracker.md`, seção "Evidence gap"): a evidência por imagem vive em `pblabs-mcp-index/servers/notes/security-scan-5d761f7-c1f36791.json`, e o relatório bruto fica no host. **Se esta imagem for publicada, o relatório bruto deve ser arquivado em `pblabs-mcp-index/servers/notes/` e a seção do tracker atualizada com caminho e SHA-256 antes de a release ser curada.**
- **O gate de scan do builder é o host, e hoje ele é apenas informative.** A receita `canonical` está com `scanGate: report-only`: o scan é executado e registrado, mas não bloqueia o job. Para que "scan limpo" seja gate de verdade, o operador precisa fixar severidade de rejeição na política do host (`POSITRONIC_EXECUTOR_MAINTENANCE_POLICY_FILE`). Decisão do owner em 2026-11-08: não criar gate paralelo no GitHub Actions, para não duplicar o gate do host.
- **O build da árvore atual falha no host.** Dois jobs de build para o commit `b0b25cfd74768650de6118e6d927c17505759dc4` (receitas `canonical`, `contextSha256` `fa0041c748ce7f6867c8af6ecd2063a826201eafb64cf4ab4bcb282c079662d3`) terminaram com `phase-failed`, fase `build` exit 1, em ~9 s cada: jobs `1c7c4614f7067ed0c8a7d516fd576d0b816140724fd85ae70fb7dae5c7121e08` (2026-11-08T18:04:44Z) e `1e94c5a9d118a599b1aca8cec7672686a401c564003eca5999df9c036b7a7873` (2026-11-08T18:11:10Z). O recibo não expõe log de build; o mesmo host executou o scan acima sem falha, então a causa está na fase de build e só pode ser vista no host. Consequência: **não existe candidato novo para a revisão `b0b25cf`**, e o scan deste documento cobre a revisão `5d761f7`, não a árvore atual.
  - **Diagnóstico apurado em 2026-11-08 (leitura do executor):** a fase de build executa `docker buildx build --platform <recipe> --network <recipe> --provenance=false --output type=docker,rewrite-timestamp=true --iidfile … --file <recipe.dockerfile> --build-arg … .` e o executor **descarta o stderr** (`child.stderr.resume()`), então o recibo nunca carrega a causa. O `recipeSha256` permaneceu `b98957d6bf0d146a9e53cfc9d12217455ee183f56f70d3e5a8731f140d8194a7` em todas as tentativas, provando que a receita (e portanto `network`, `rejectSeverities`, `timeoutMs`) é resolvida quando o executor carrega a policy — uma mudança do lado do projeto só entra em vigor com um restart do executor. A receita `canonical` deste projeto foi registrada em 2026-11-07 e **nunca executou um build pelo executor**: a operação de imagem exercitada até aqui foi só o scan do pin. Portanto a falha de hoje é do primeiro build por esse caminho, não uma regressão do produto.
  - **Experimento prepared:** um `Dockerfile.probe` sem rede (`FROM scratch`) e o override `operations.image.dockerfile` em `.positronic/project.json` separariam "buildx/Engine" de "passos de rede do Dockerfile". Ambos foram removidos do repositório depois de se mostrarem inaplicáveis sem restart do executor; o conteúdo está no histórico (`3d21205`) e o procedimento de ativação é o mesmo.
  - **Ações do host (fora do container do agente):** (a) rodar o `docker buildx build` da receita diretamente no host, com o mesmo `--network` da policy, para obter o stderr; (b) se o `--network` estiver `none`, fixar `default` nos defaults `registeredProjects` da policy de manutenção; (c) com o build passando, `scan + image_authorize + update-image + configure + discover + activate` e a validação MCP antes de aprovar o pin.

A publicação dos commits locais pelo executor responde `source-invalid` para
este repositório, inclusive em dry-run sem efeito (alvo igual ao remoto).
`vcs_status` funciona e devolve o OID remoto atual

Diagnóstico apurado em 2026-11-08 por leitura do executor: `source-invalid` é o
código de fallback para qualquer erro não tipificado no dry-run — `lstat` do
`hostRoot` inexistente, falha de `git init`/`cat-file`/`fsck`/`pack-objects` na
cópia congelada, ou layout de objetos inválido. O repositório passa todas as
validações de forma locais replicadas (`sourceRoot`: caminho canônico, uid,
modo, `.git`, `.git/objects`, `.git/objects/info`, sem `alternates`/`commondir`/
`shallow`), a cópia congelada reproduzida localmente aceita o commit alvo
(`cat-file`, `fsck --strict`, `merge-base --is-ancestor`, `rev-list`), e não há
`core.hooksPath`, `include.path` nem hook `pre-push` — o ramo `checks: none` do
publicador passa. Logo a causa é do lado do host: `hostRoot` do grant apontando
para outro clone (sem o commit alvo) ou um clone do host desatualizado. A
publicação continua sendo necessária para que as correções e esta evidência
existam em `origin/main`.

O bundle do journal deste projeto está vazio e `journal_request`/`journal_read`
no `projectKey` retornam `not-found`; a nota durável do ciclo foi gravada no
